### Decisions

| # | Decision | Why |
|---|---|---|
| **1A** | Drafting is a built-in `draft-graph` run. Save in the builder is the approval. It is not a server route and not a run with an approval node. | The run gets the log, cost, transcript, park and reply for free, and the outputs `check` hook already gives a repair turn. `slice-decision.ts` is ghost-specific, and `saveBuilderGraph` already does the verified, transactional write. |
| **2A** | A `graphs:catalog` command built-in publishes what the drafter knows, computed from the live tables. It carries prompt ids, not bodies (B). | It can't drift as built-ins are added (two were added last week). All six built-in specs measured 19k chars in total, under the 64k context cap. |
| **3A + C** | `draftProblems(spec, base)` is node-free in `core/graph-spec.ts` and runs as part of the outputs check (rules listed below this table). | The rules follow what actually grants power. "Copied" has a real definition (B). `runs:launch` without its approval gate is a mass side effect. |
| **4A** | Optional `GraphSpec.drafted = { run, draftHash }`, dropped at compile time like `position` and kept on save. `draftHash` is taken after the same normalisation the builder applies on load (outside finding 6). | Without it the success metric can't be measured. Provenance is part of the artifact for the same reason `position` is. SPEC_VERSION stays 1. |
| **5A** | `specProblems(spec, { knownPrompts, bodies })` checks bodies when given: no `{{>`, every agent step has a body, no orphan bodies, and reads equal `templateReads(body)`. The browser, the save route and the draft check all pass bodies. | One verdict (HOW-22). |
| **6A** | One repair turn, using the executor's existing `repairSent`. A second refusal fails the attempt (`claude.ts:607`) and the engine parks it (`run.ts:569`) with the problems quoted. A reply re-runs the step in a fresh session. The refused draft can still be read from the final message via `locateOutputs`. | No new loop to build. |
| **7A** | Item 7 is accepted as shipped (warn before destroying, no undo). "Reopen the original draft" moves to phase 1b. | A one-action undo stack is a special case that rots. |
| **8A** | A 6-case eval for the drafter, run through `reviser/eval/ab.ts` (phase 1b). | This is the first prompt whose output is fully machine-checkable. |
| **A** | Phase 1 shows a minimal diff list against `based_on`. The canvas overlay stays phase 2. | Otherwise you'd approve a ~15-step draft on the screen HOW-31 says made no sense. |
| **B** | A draft body is either text or `{copyOf: <catalog prompt id>}`. Save materialises copies (includes expanded, as at pin time) into `<name>.<step>` files. | `builder.ts:152` forces drafts to own their prompts, and 5A bans `{{>`. Without `copyOf`, the agent re-types about 25k chars of base prompts as JSON (twice if repaired) and can garble them unseen. |
| **E** | The draft check fails closed when `graphs.catalog` is missing from the step's reads. A graph test pins that the drafter reads it. | A check that passes when its evidence is missing breaks "nothing dead-ends silently". |
| **F** | Finishing adds a "Ready for you" entry (not the amber alarm, D-7A). It resolves when the draft is saved or discarded. | Otherwise a finished draft sits unseen. |
| **D** | H2, H3 and H6 ship first as their own change. Provenance stays in phase 1; metrics, eval and reopen move to 1b. | They fix bugs that exist today. A graph saved before provenance exists can never be measured. |

**The `draftProblems` rules (3A + C):**
- Commands must be `COMMAND_BUILTINS`, and `runs:launch` is banned.
- No `approval` steps.
- `defaults` must equal the base's, or be absent when there is no base.
- No per-step `config`.
- A step whose body is `copyOf` a base prompt keeps that base step's `readOnly`.
- Any new agent step without `readOnly` is a permission callout on the review agenda.

Whether a spec-built approval step actually fails at run time is **unverified** (confidence 6). It is excluded either way, because nothing can validate its proposal.

## Design (from /plan-design-review, 2026-10-13)

The conversation is the centre. The canvas is for hand edits only. Wireframes, on the real
tokens, are attached to HOW-56: `final-C.png` (the card and its receipt) and `final-A.png`
(the review page).

```
 New run → "Draft a graph" (one intent field, optional base + workspace)      (D-1B)
        ▼
 the draft run's Chat:  your request → live progress line (HOW-49) → DRAFT CARD
   ┌ name [editable] · based on X ··················· [Review all changes] [Save | Review and save]
   │ summary: ⚠ N steps can change your code · N blocking · ⓘ N worth a look
   │ Can change your code → What changed (− + ◐, cascades named, body diffs) → Unchanged (collapsed)
   │ → Worth a look → Ask for changes [labelled section, own button] → Discard this draft
   └ after Save: receipt "✓ Saved as X · not edited / edited on canvas · Open · Run it"
        │ Review all changes
        ▼
 /runs/:id/draft  review page: same list + 420px diagram (removed steps ghosted)
        │ Open on canvas / fix on canvas
        ▼
 builder canvas, header "Editing draft from run X · back to review"; Save there = same save
```

| # | Decision |
|---|---|
| **D-1B** | The way in is New run, with `draft-graph` as an ordinary graph whose launch form shows one intent field, an optional base (default: let the agent choose) and an optional workspace. It is not a new composer on Graphs. |
| **D-2A** | Order is risk, then changes, then advice. A header summary line comes first. Empty sections render as one line, "Nothing flagged". Glyphs carry meaning (− removed, + added, ◐ changed, ⚠ can change your code); colour appears only in body diffs (`--diff-add`/`--diff-del`). |
| **D-3A** | The diagram reuses `GraphDag`, read-only. Removed steps are dashed, struck through and marked −, with no edges into them. Focusing or hovering a list row highlights its box. |
| **D-4A** | State table (below) is adopted, and doubles as the component-test matrix. |
| **D-5A** | "Ask for changes" is a labelled section inside the card with its own button. It is never a second composer (HOW-27). It launches a new `draft-graph` run with `--parent <this run>`, taking the original request, the change and this draft as the base. The old card shows "Redrafted → run Y". The new run's Chat shows both requests. |
| **D-6A** | The card offers Save directly only when the draft grants no NEW write access compared with its base. Otherwise the primary button is "Review and save". |
| **D-7A** | A ready draft is a quiet "Ready for you" group in Needs you: neutral glyph, no amber, no chime, no favicon change, counted separately in the rail. A twice-refused draft is a real park and keeps the full alarm. DESIGN.md gains a line recording this (T9). |
| **D-8A** | Keyboard, screen-reader and width spec as below. |
| **D-9A** | The graph name is an inline editable field (the builder's name rule and `nameTakenProblem`). A rename is excluded from the "edited before save" hash, like positions. A name-taken 409 focuses the field. Prompt ids are materialised under the final name at save. |
| **D-10A** | The canvas edits the same draft. Saving there keeps `drafted` and marks it edited. The card and page work out "saved" from any saved graph whose `drafted.run` is this run, so nothing offers a second Save. Discard is a decision event (`draft-discarded`) in the run's log, which also resolves the "Ready for you" entry. |

### Keyboard, screen readers, width (D-8A)

- **Keyboard:** Tab order is summary → Save/Review → each section's rows → Ask for changes → Discard. Rows are focusable, and focus highlights the diagram box. "Unchanged · show" is a disclosure button with `aria-expanded`. Body diffs over 20 lines collapse to "show all N lines".
- **Screen readers:** every glyph has a text label. Sections are headed regions. Diffs use `<del>`/`<ins>`.
- **Width:** at 1280px and above, the list and the 420px diagram sit side by side. Below that, the diagram moves under the list, collapsed behind "Show the draft". The card follows the chat column and never shows the diagram.
