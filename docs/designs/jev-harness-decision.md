## Problem Statement

Howdah runs agents at each vendor's own permission level (claude forced `auto`; codex a
`danger-full-access` sandbox but with `approvalPolicy: "on-request"`, so it asks anyway;
cursor `--force`) and has no policy of its own about WHICH actions are dangerous. That
classifier lives inside three closed harnesses.

**Corrected 2026-09-26 after review.** The first draft said "two of them (codex, cursor)
cannot be asked mid-turn". That is wrong: `engine/executors/codex.ts:104` `answerApproval`,
called at :163, with `approvalPolicy: "on-request"` at :186 and a file header at :7-9 saying
approvals are *"routed through the same attention round-trip as claude"*. **Only cursor
cannot be asked** — and cursor is `optional` in `core/harnesses.ts` and has never executed a
node here (384/384 `prompt-rendered` events are claude). HOW-17's fallback chain can still
hop a node onto cursor; the harness change IS logged (`prompt-rendered.harness`), the
resolved per-attempt `permissionMode` is not.

LangChain's post names exactly this: *"this classifier step has been locked away in the closed
source parts of the harness"*, and argues a cheap calibrated classifier now makes it ownable.

## What Makes This Cool

Not "a safer harness". The interesting version is that **the policy becomes a drawn,
versioned, diffable artifact** rather than thresholds buried in someone else's binary. Howdah
already has a canvas where conditions are typed data and a validator that explains refusals in
the operator's own words. A policy is a decision structure. Howdah already owns a decision
engine.

## Constraints

- Single user, personal tool. No customers, no adoption argument.
- 12 runs of history, all on claude. Zero observed destructive incidents.
- jev-1.13: 32k state, text only, numbers unreliable for arithmetic.
- No API key yet; nothing live has been run.
- Howdah must keep working offline against local CLIs.

## Premises

All five agreed by the operator:

1. Howdah's permission policy is genuinely unowned: three vendor policies, two unaskable, a
   fallback chain that hops between them silently. `readOnly` is the only lever held locally.
2. There is no evidence the threat has materialised. 12 runs, all claude, zero incidents.
   Real in principle, unobserved in practice.
3. The canvas cannot express a threshold today. `core/graph-spec.ts:85` `PREDICATE_OPS` has
   no comparison operator.
4. `greater-than` is worth adding regardless of whether the classifier ships. A builder that
   offers a `number` field kind and only `equals` is incomplete on its own terms.
5. Observe-only is the only honest first move: nothing satisfies R5 because no corpus exists.

## EUREKA

`FieldKind` includes `"number"`, but `PREDICATE_OPS` is `equals, not-equals, one-of, is-true,
is-false, is-empty, is-not-empty`. **No graph on the canvas can route on "score above X".**
Nothing has hit this because no built-in graph routes on a number.

🟡 **Narrowed after review.** Two of Jev's three answer types are numeric (`noul` 0-1,
`score`), and both carry `confidence`. The third, `choice`, returns a **string**, which
`equals`/`one-of` already handle. So the operator is the precondition for any integration
routing on a `noul` or a `score` — not literally every one. Note the companion's own Shape A1
proposes a risk **Choice**, so the flagship classifier may not need it at all. It is still a
defect on the builder's own terms: a `number` field you cannot compare.

## Approaches Considered

### Approach A: Probe first, ship one defect fix — SELECTED
Add `greater-than`/`less-than` to the predicate vocabulary, then replay existing `run.jsonl`
tool calls through Jev in a throwaway script and report what a policy would have caught.
Effort S. Risk low. Completeness 3/10 by design: it is a measurement, not a feature.

### Approach C: The policy IS a graph
One `policy:judge` command built-in writes Jev's numbers into context; the policy is then
edges on the canvas, reusing routing, weights, park-on-no-match, the log and replay. Effort M.
Ceiling: a graph node runs BETWEEN nodes, so mid-turn tool interception is permanently out of
reach this way.

### Approach B: The shaping doc as written (D then C)
`systemone/policy.ts` with its own questions, thresholds and `policy-judged` event, wired both
pre-flight and at claude's `can_use_tool` seam. Effort L. Rejected for now: builds a second
decision engine beside `engine/run.ts`, on the least evidence of any option.

### Rejected during the session
- **Shape A (wire-only)**: claude-only, so two of three harnesses stay ungoverned and a
  fallback hop escapes the policy entirely. Dead on the fit check.
- **Park it and do Tier A instead**: Tier A has no corpus either, so it would ship on the same
  safety argument with none of the evidence this probe produces.

## Recommended Approach

**A ("probe first, ship one defect fix"), then reassess.** The question asked was whether this is worth working on. A is the only
option that answers it with measurement rather than argument, and its one shipped change is a
defect fix that stands alone if the classifier is never built.

## O1 answered (2026-09-26)

Tool **names** survive in full: 5,050 `tool_call` chunks, 18 distinct tools.
Tool **inputs** survive as complete JSON up to a hard **400-char cap** —
`engine/executors/claude.ts:212` `JSON.stringify(ev.input).slice(0, 400)`, repeated verbatim
at `codex.ts:157` and `cursor.ts:121`.

| Measure | Value |
|---|---|
| `tool_call` chunks | 5,050 |
| Truncated at the cap | **1,044 (20.7%)** |
| Bash share of all calls | 4,508 (89%) |
| Bash calls truncated | 899 (19.9% of Bash) |
| Median input length | 173 chars |

So the corpus is **79% complete, and the missing 21% is concentrated in Bash** — the tool the
classifier exists to judge. The plan needs the branch it did not have: raise the cap going
forward (it is a bare `400`, no named constant) and treat the historical corpus as a
lower bound, OR re-run live. `tool_result` content is capped the same way, so outcome ground
truth is lossy too.

**The cap is a logging artifact, not a design limit.** `answerPermission` (`claude.ts:159`)
and `answerApproval` (`codex.ts:104`) both receive the full `input` object unsliced. Live
classification sees everything; only the retrospective replay is degraded.

**What the corpus contains:** 56 `rm -rf`, every one targeting `/tmp` or a local temp dir;
3 force-pushes, all `--force-with-lease` to the run's own `howdah/<run-id>` branch; 1 `sudo`,
a false positive inside a test-file edit. The one alarming-looking line,
`rm -rf $HOWDAH_HOME`, is safe because `HOWDAH_HOME` is reassigned to `/tmp` earlier in the
same command — which is the best argument in this document for a semantic classifier over a
regex, and also the best argument that a 400-char window is not enough to be one.

## Change surface for the comparison operator

Sized by review. 4 of the 5 non-trivial sites fail **silently** — write the test first.

| Site | Compiler catches it? |
|---|---|
| `core/graph-spec.ts:80-83` `Predicate` union | n/a, the change itself |
| `core/graph-spec.ts:357` `predicateLabel` | **YES** — exhaustive switch, no default |
| `core/graph-spec.ts:371` `compilePredicate` | **NO** — ternary chain falls through to `is-not-empty`, so a threshold silently routes on presence |
| `core/graph-spec.ts:165` `recoercePredicate` | **NO** — returns `base` unchanged; a field flipped text→number leaves `> "5"` a string. This is HOW-22 finding 3 verbatim |
| `core/graph-spec.ts:149` operand extraction in `unmatchableOperand` | **NO** — new op silently exempt from the check |
| `web/app/builder/branching.tsx:72` `operandText`, `:85` `repredicate`, `:59` `OPS` | **NO** — operand box renders empty and stores nothing |
| `web/app/lib/spec-draft.ts:162` `seedPredicate` | no |
| `core/graph-spec.ts:971` `parsePredicate` | **NO** — `oneOf(v.op, PREDICATE_OPS)` accepts it, the value branch does not handle it |

**Runtime semantics, unspecified in the first draft:** `coerceOperand` types the operand, not
the runtime value, which arrives from a command's final JSON line and may be a string, `null`
or absent. Specify `typeof at(v) === "number" && at(v) > p.value` — a non-number never
matches, mirroring `is-true`'s `=== true` — and pin it in a test. Also decide `>=`/`<=`:
Jev's `noul` is a 0-1 float where `>= 0.8` is the natural spelling.

## Success Criteria

- `greater-than`/`less-than` land in `PREDICATE_OPS` with `specProblems` and the condition row
  UI understanding them, and `bun test` green.
- 🟡 **A measured FALSE-POSITIVE RATE**, with a pass/fail threshold set BEFORE the run. The
  original criterion ("a report naming every action a policy would have flagged, or stating
  there were none") cannot fail: on a corpus with zero known-bad actions, a policy that flags
  nothing is indistinguishable from a policy that is broken. The only signal 12 clean runs can
  give is how many of 5,050 known-safe actions the policy would have blocked or parked.
