## Premise challenge

The ticket's title blames complexity. The evidence blames the words "by hand".

HOW-31 is the fourth ticket about this surface: HOW-22 "Re-do create graph", HOW-24 "The
current workflow / graph creator is very confusing", HOW-26 "I made a new graph using the new
mechanism but everything looks weird", all Done. Three rebuilds (wizard, canvas, advice at two
severities) and the complaint returned each time. The operator's own account of HOW-31: *"I was
trying to build a new graph for my coding workflow and basically broke everything, none of it
made sense and I gave up and used the ones we had."*

A fourth repair of the authoring surface is how HOW-33 gets filed.

## EUREKA

Howdah owns both halves of graph generation and uses neither.

* `specProblems()` (`core/graph-spec.ts`) is a complete VERIFIER. It explains every defect in
  the operator's own words, attributed to a step and the pane that fixes it, and
  `buildGraph(draft).validate()` is node-free so it runs in the browser on every keystroke.
* The product's entire purpose is running agents that GENERATE.
* `approval` nodes, `engine/slice-decision.ts` and the ghost/proposal machinery are a built,
  tested, round-keyed PROPOSE-THEN-HUMAN-APPROVES primitive, applied to code and never to
  Howdah's own graphs.

Hand-authoring a GraphSpec in a GUI is the one task Howdah refuses to point itself at.

## Vision

### 10x check

The 10x version is not a better canvas. It is the canvas ceasing to be where work starts.
Today the builder requires the engine's whole vocabulary up front: field freshness, step ids
that double as prompt filenames, Otherwise edges, produces versus reads. Approach B removes
that for the first draft. The 10x move removes it for every later change too, by making
editing a conversation about the graph rather than a form over its data structure.

### Platonic ideal

Three weeks into a Kotlin service you type: *"like implement-ticket, but run the Gradle build
before review and skip the PR, I'll push myself."* Howdah shows a five-step graph, two steps
lifted from implement-ticket unchanged, one new command step carrying your actual build
command, and a note: **"I dropped delivery.publish and its three repair steps. That also
removed the probe_pr loop."** You read the diff, not the spec. You press Run. Nothing was
typed into a form.

## Accepted Scope

* Agent drafts a `GraphSpec` from described intent, seeded by run history.
* `specProblems()` runs against the agent's output before the operator sees it; failures go
  back to the agent to redraft. The operator only ever sees valid graphs.
* The agent writes prompt bodies for every agent step it proposes.
* The canvas renders a proposal as a DIFF against the nearest existing graph, listing steps
  unchanged, added and removed, and stating explicitly what a removal cascaded into.
* A control on a finished run that seeds a draft from what that run did.
* `remove-field` is made honest: state what will be removed (branches that tested it, prompt
  bodies that name it) before it happens, and add undo.

## Review corrections (2026-10-08)

Adversarial review scored the first draft **5/10**. Four findings verified against the repo.

### B1 (BLOCKER) — built-in graphs have no `GraphSpec`

`GraphDef.spec` is optional (`core/graph.ts:265`) and set only by `buildGraph`
(`graphs/builder.ts`). All eight built-ins use `defineGraph`, and `graphs/builder.ts` refuses
to infer a spec from TypeScript by design (a file it cannot re-parse reads as `builder: false`).

**Items 2, 3 and 5 all rest on diffing or seeding against built-ins.** On this machine that is
every graph and all 14 runs. The Platonic ideal's own worked example ("two steps lifted from
implement-ticket unchanged") requires exactly the inference the codebase refuses.

Options: (a) hand-write `GraphSpec` literals for the built-ins so they round-trip, which also
makes the presets builder-editable (star 3 on this plan's own ladder); (b) synthesise a lossy
spec from a compiled `Graph` for DIFF only, never for save; (c) scope items 3 and 5 to
builder-made graphs, which here means zero graphs.

### H1 (SAFETY, unscoped in the first draft) — a drafted graph contains LLM-authored shell

`core/graph-spec.ts:692` checks only `!n.run.trim()`. A command node's `run` is `bash -c` in
the operator's worktree. The verifier has no opinion about its contents, so **"the operator
only ever sees valid graphs" is true and dangerous**: valid is not safe.

`COMMAND_BUILTINS` already exists as a table. Restricting drafted graphs to built-ins for v1
is the cheap answer; review-before-run on `run` is the general one.

### H4 (UNASKED) — which severity gates the redraft loop

`graphs/builder.ts:199` filters `isBlocking`, deliberately, defended in comment. **Every
defect HOW-26 was filed about was `advice`**, not blocking (`core/graph-spec.ts:825-842` lists
them: agent steps told nothing, a verdict on the launch field, branches on free text). So a
loop gating on blocking can reproduce HOW-26 verbatim and still report success. Gating on
advice too makes item 4 larger and risks refusing legitimate graphs, because advice carries
deliberate carve-outs for a human reader.

**This decides whether the feature fixes HOW-31 or renames it.** O2 did not ask it.

## Decisions after review (2026-10-08)

| # | Decision |
|---|----------|
| **D4 / B1** | **Hand-write `GraphSpec` literals for the eight built-ins** so they compile through `buildGraph` like any builder-made graph. Unblocks items 2, 3 and 5 in one move, and makes the presets builder-editable (star 3). Watch `core/graph-spec.test.ts`, which pins the exact compile output. |
| **D5 / H1** | **v1 drafted graphs may use `COMMAND_BUILTINS` only.** No free-form `bash -c` from an agent. Arbitrary shell stays a thing the operator types. Revisit once drafting is proven. |
| **D6 / H4** | **Blocking gates the agent; advice becomes the operator's review agenda.** The agent redrafts until `specProblems` reports nothing blocking (the same verdict `graphs/builder.ts:199` already enforces, not a second one). The advice tier is NOT auto-cleared: it is rendered as the list of things the human is reviewing. This gives `advice` the job HOW-26 built it for and is what stops this loop reproducing HOW-26. |
| **D7** | Item 2 stays accepted but **sequenced last**: ship 1 + 3 + 4 + 7, then add history seeding once the drafts have been seen. 14 runs over 2 shapes is a thin corpus to tune against before anything has shipped. |

### Build order

1. **B1** — `GraphSpec` literals for the built-ins. Everything else depends on it.
2. **Item 7** — `remove-field` honesty + undo scoped to that action. Editing proposals is now the main interaction.
3. **Item 1 + 4** — the drafting agent (read-only; the save route writes), prompt bodies, redraft on blocking. Item 4 is **M**, not S.
4. **Item 3** — proposal as a structural diff against the nearest spec, with advice as the review agenda.
5. **Item 5** — author from a finished run.
6. **Item 2** — history seeding, once 1-5 are in use.
