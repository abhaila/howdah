## Problem Statement

Howdah is meant to become the only tool used for development work, at home (personal Kotlin/http4k
+ React/TS projects) and at work (the Sequence monorepo: Kotlin http4k routes, Spring controllers,
a React frontend). Today three things send the operator back to plain Claude Code / Codex / the IDE:
design back-and-forth on structure, quick interactive edits, and missing workflows.

The first is the sharpest. `implement-ticket` runs `plan → implement → local_review` with the plan
as one free-text string (`graphs/implement-ticket.ts`) and no human gate before code. Design
decisions — module structure, call stack, names, unnecessary casts — end up in long prose
(`shaping.md`, 734 lines) that the operator has stopped reading. By the time structure is visible,
it is already code.

## What Makes This Cool

- **The design surface is a map, not a document.** A code-derived system map (reference: an
  isometric "repository system map" with planes, zones, a request-path rail, a *What it does / How
  it's built* panel and a steppable trace). A vertical slice is one highlighted path through it.
- **The agent proposes the next slice as ghosts** — dashed blocks, edges and trace steps — and the
  operator steers by pinning comments to them before any code exists.
- **After the build, ghosts are checked against reality.** Re-extraction turns verified ghosts
  solid and flags drift. Research across ~25 tools found nobody closing this loop: IcePanel
  proposes future states but never checks them against code, CodeRabbit diagrams changes only
  after they are written, Windsurf Codemaps are snapshots.
- **Every edge says how it is known** (observed / resolved / syntactic / evidence-checked /
  unresolved), by glyph. The map never presents a guess as fact — the same rule
  `reconstructRender()` applies to prompts.

## Constraints

- **General-purpose.** Languages and frameworks are adapters; the core knows nothing about Kotlin,
  Spring or React (mirrors `adapter/` + `capabilities.ts` for harnesses).
- **Precise.** Nothing solid unless something proved it; "not checked" is distinct from "drift".
- **Howdah invariants hold.** The log is the only storage of facts; map snapshots are immutable
  run-dir manifests referenced by hash (like pinned prompts) over an immutable content-addressed
  object store; solid/ghost/drift are derived in `web/derive.ts`; nothing dead-ends silently.
- **Local-only surface.** The viewer binds loopback and refuses cross-origin writes (Sprint 0.4).
- **Monorepo scale.** tree-sitter is cheap enough to run repo-wide and cache; SCIP and rendering
  are scoped to a neighbourhood (defined below).
- **Subscription auth.** Efficiency means allowance, not API dollars.
- **Work use.** Sequence code is proprietary; state stays in local `HOWDAH_HOME`.

## Premises (agreed)

1. **Order:** sprint (c) the map first; sprint (a) competitor survey runs in the background as a
   Howdah `research` run; sprint (b) memory comes after (c) because it queries what (c) builds.
2. **Zoom:** a block is a module/package; a trace step is a function; names and casts live in the
   selected block's *How it's built* panel, only for code the slice touches.
3. **Memory reframed:** no vector DB / Obsidian until a measurement demands it. "Memory" = agents
   query the map and run log RLM-style (arXiv 2512.24601) instead of preloading docs. Research
   supports this: Claude Code, Cognition, Continue and Cody all moved off embedding retrieval;
   measured gains were small (Copilot 2% time, Cursor +0.3% code retention).
4. **Success test:** real tickets designed on the map, not in `.md` files (measured below).

## Decisions

- **SM-D1 — "Vertical slices" means how Howdah builds other projects**, not restructuring Howdah's
  own folders.
- **SM-D2 — Steering is pinned comments**, batched and sent; the agent redraws ghosts; the operator
  approves. Comments are run-log events and feed the reviser. *Ruled out:* live chat pairing
  (operator rejected it); whole-slice approve/reject (can't point at the wrong thing); direct map
  editing (several times the work — possible later).
- **SM-D3 — Map source is code plus a ghost slice.** Existing structure is extracted from real code;
  the proposed slice is agent-drawn ghosts that solidify only when re-extraction observes them.
  *Ruled out:* agent-drawn maps (drift like the doc); code-only maps (no way to steer before code).
- **SM-D4 — Layered extraction, SCIP in slice 2.** Each layer is authoritative only for what it can
  prove:

  | Layer | Final say on | When |
  |---|---|---|
  | tree-sitter + framework adapters | routes, fetch sites, blocks, identifier and cast *inventories*, possible paths | always; cached per file |
  | SCIP (scip-java for Java+Kotlin, scip-typescript) | definitions, references, call edges, implementation candidates | whenever a build succeeds — always after a slice is built |
  | compiler / linter (kotlinc `USELESS_CAST`, javac `-Xlint:cast`, typescript-eslint) | "unnecessary cast" judgements | same build, compile tasks forced to rerun; otherwise "not judged" |
  | agent + checker | nothing on its own; fills unresolved gaps with verified file:line evidence | only on unresolved edges; never overrides a higher layer |
  | runtime (OTel spans from tests, Spring actuator) | execution order, real DI graph | roadmap |

  *Ruled out:* language servers as the record of truth — kotlin-lsp is Alpha, and issue #254 plus a
  2026-09-15 write-up show call hierarchy silently dropping Java, safe-call and test-source-set
  edges; wrong-but-complete-looking answers disqualify it for a precision tool. Joern (JDK 21,
  security-oriented) and syntax-only (leaves Spring DI and casts unjudged) also ruled out.
- **SM-D5 — Sprint 0 fixes five verified problems before slice 1**, because slice 1 builds directly
  on the code paths they break: prompt proof, human replies, loop bounds (office hours), plus the
  network-exposed viewer and duplicate log sequence numbers (eng review).

## Cross-Model Perspective (Codex cold read)

- Make the map an **executable design rehearsal**: pick a scenario (valid / overlap / DB failure),
  step through the proposed slice; pins become architectural constraints **and acceptance tests**.
  *Adopted, deferred to the roadmap (scenarios & motion).*
- Bind approval to the **proposal hash and source snapshot**; a redraw or changed baseline
  invalidates it; test that restart cannot bypass approval. *Adopted in slice 1.*
- A static call hierarchy does not give execution order — animated traces need a visible basis.
  *Adopted: static traces are labelled "possible path".*
- Suggested Joern for extraction. *Not adopted* (SM-D4). Its point that generic call analysis can't
  find React → http4k/Spring boundaries stands and is handled by framework adapters.

## Recommended Approach

### Sprint 0 — fix what the map would build on (CC ~1.5 days; human ~1.5 weeks)

Each verified against source on 2026-09-19.

**0.1 The prompt proof omits what is sent.** `engine/run.ts:374` hashes the render; afterwards
`engine/executors/claude.ts:45-46` appends a skill hint and the outputs contract, and
`engine/executors/codex.ts:39` appends the outputs contract. `rendered_hash` covers neither.
Hashing them naively would make every render UNVERIFIED, because `reconstructRender()`
(`prompts/library.ts:379-399`) rebuilds only from the pinned template, `context_read` and jump
suffixes — skills aren't logged, and write keys come from unpinned graph code. Fix:
- Build every suffix in one place (`core/template.ts`, the single render implementation) and apply
  them in `Engine.renderPrompt` *before* hashing; executors send `renderedPrompt` unchanged.
- **Fixed order:** template body → operator jump suffix → operator reply suffix (0.2) → skill hint →
  outputs contract. Per-harness behaviour is preserved: the skill hint is applied to every harness
  except `codex`. That includes `opencode`, which today falls through to the claude executor
  (`executors/index.ts:62`) and gets the hint. Codex never got one, and this fix does not change
  that.
- Log the inputs on `prompt-rendered` (additive optional fields): `skills: string[]`,
  `output_keys: string[]`, `suffix_version: number`. `core/template.ts` keeps each suffix builder
  keyed by version, so rewording a suffix later bumps the version instead of silently turning old
  renders UNVERIFIED.
- Extend `reconstructRender()` to rebuild with the logged version's builders. Old events without the
  fields keep today's behaviour (verified against the old, shorter text).
- Tests: for both harnesses, hash(bytes passed to the spawned CLI) == logged `rendered_hash`;
  reconstruction verifies with skills, without skills, with a jump suffix, with a reply suffix, and
  for an event rendered under an older `suffix_version`.

**0.2 Replies to a park never reach the agent.** `cli/main.ts:281` and the web reply route log
`attention-resolved.reply`; nothing renders it (only jump messages, `run.ts:365-369`). Today the
park reason is free text (`log/events.ts:142`), so the fix first adds an additive `code` to new
`attention-raised` events. What a reply does is then defined per code:

| `code` | Raised by | Reply behaviour after the fix |
|---|---|---|
| `attempt-failed` (agent node) | a failed agent attempt | resume re-attempts the node; the reply is rendered as an operator suffix, consumed once |
| `attempt-failed` (command / worktree node) | a failed non-agent attempt | **refuses**: no prompt to carry it; "fix the cause, then `resume`" |
| `executor-threw` | an executor exception | agent node: as `attempt-failed`; other kinds: refuses as above |
| `max-visits` | `run.ts:216-217` | **refuses** with "use `jump <node> <msg>`" — which now works (see 0.3 jump reset) |
| `no-edge` | exhausted conditions | refuses, same message |
| `max-steps` | `run.ts:248` | refuses, same message |
| `ambiguous-effect` | resume probe says `unknown` | refuses with "resolve the effect first" — out of scope for Sprint 0 |
| `awaiting-approval` | slice 1's approval node | refuses: use `approve` / `send-feedback` / `redesign` |
| `approval-missing` | slice 1's `requires` gate | refuses: use `approve`, or `redesign <run> <msg>` |
| `stale-base` | slice 1's first-implement live check | refuses: use `redesign <run> <msg>` (re-extracts) |
| harness permission ask (mid-node) | `claude.ts` / `codex.ts` | unchanged (live `reply.ts` path) |

Old events without `code` fall back to today's behaviour (logged, not rendered).

- The reply rules live in one shared `resolveReply()` (in `engine/control.ts`), used by both
  `cli/main.ts:273-287` and `web/server.ts:350-358` — today that logic is duplicated. The slice 1
  comment/approval routes use the same shared module.
- Only one reply per ask is possible already (`replyCommand` throws once resolved), so no stacking.
- `resume()`'s own `attention-resolved` with `reply: "resume"` (`run.ts:180`) must never render:
  add an additive `source: "operator" | "resume"` field to new `attention-resolved` events and render
  only `operator` replies (old events without the field: treat `reply === "resume"` as resume).
- `reconstructRender()` gains reply candidates alongside jump candidates.
- Tests: one per row above, plus "resume's own resolution is not rendered".

**0.3 Review loops in `implement-ticket` are bounded only by `maxSteps` (1000), and a `maxVisits`
park has no working escape.**
- `implementation.local_review → plan_review → implement_review → local_review`: add
  `maxVisits: 3` to `implementation.plan_review`.
- `delivery.review_repairs ⇄ delivery.revise_repairs`: add `maxVisits: 3` to
  `delivery.revise_repairs`.
- The repair → publish cycle (`fix_ci`/`address_reviews`/`resolve_conflicts` → `review_repairs`
  (pass) → `publish` → `probe_pr` → `CI_FAILED` …): add `maxVisits: 5` to `delivery.publish`.
- The `probe_pr ⇄ wait 5m` poll stays deliberately unbounded except by `maxSteps`: it waits on a
  human reviewer.
- **Jump resets visit *budgets*, not visit numbers.** Visits are cumulative today and
  `operator-jump` does not reset them, so after a `maxVisits` park, `jump` to that node re-parks
  immediately.
  - Visit numbers must stay monotonic: `${node}#${visit}` attempt ids (`run.ts:220`), side-effect
    `attempt_id`s and `web/derive.ts`'s `${node}@${visit}` rows all rely on them.
  - Instead, new `operator-jump` events carry an additive `reset_budgets: true` (the CLI and web
    default). Replay records a per-node `floor[node] = visits[node]` for **every** node at that
    event: the operator has taken responsibility for the run.
  - The check becomes `visit - (floor[node] ?? 0) > maxVisits`.
  - Old events without the field replay as today.
- Tests:
  - An always-rejecting reviewer parks each loop with code `max-visits`.
  - `jump <node> <msg>` then makes progress, with the message rendered.
  - Visit numbers after the jump continue upward, with no duplicate `node@visit`.

**0.4 The viewer is reachable from the network and from any web page** (eng review issue 1, verified
2026-09-19).
- **What's exposed today:**
  - `Bun.serve` at `web/server.ts:75` sets no `hostname`; a live probe shows `TCP *:<port> (LISTEN)`.
  - `/api/runs` (`server.ts:283`) does `await req.json()` with no content-type or `Origin` check.
  - It forwards `body.dir` and `overrides.permissionMode` to the CLI.
  - So LAN neighbours, and any web page via a no-preflight `text/plain` POST, can launch a
    `bypassPermissions` run.
- **Fix:**
  - Bind `hostname: "127.0.0.1"`.
  - One shared guard runs before every mutating route (POST/PUT/DELETE). It rejects:
    - a `Host` that isn't `localhost:<port>` or `127.0.0.1:<port>` (DNS rebinding);
    - a present `Origin` that isn't the viewer's own (CSRF);
    - a `content-type` other than `application/json` (415).
  - Requests with no `Origin` (the CLI, curl, tests) are allowed.
- **Tests:**
  - each rejection;
  - the same-origin UI works;
  - no-Origin clients work (regression);
  - the server is not listening on non-loopback addresses.

**0.5 Two writers can stamp the same `seq`, and check-then-append is not atomic** (outside voice #2,
verified).
- **The problem:** `EventLog` reads the last `seq` once, at construction (`log/write.ts:25`), then
  counts in memory. The runner and every web or CLI writer hold separate instances. This can already
  collide today when you answer a mid-node ask from the browser.
- **Fix:**
  - `append()` takes an exclusive lockfile beside `run.jsonl` (O_EXCL, with stale-lock recovery by
    PID). It re-reads the tail `seq` under the lock, stamps and fsyncs, then releases.
  - New `appendIf(check)` runs a predicate over the current events inside the same critical
    section. Decisions use it.
- **Tests:**
  - two processes appending concurrently produce unique, strictly increasing `seq`s;
  - concurrent `appendIf` decisions yield exactly one decision;
  - a stale lock is recovered;
  - the existing append/read/torn-line tests still pass (regression).

working until the slice loop has proven itself.
- **Shared delivery.** The delivery half (publish → probe → repairs → complete/cleanup) moves into one
  exported builder, `deliveryGraph({ verifyAfterRepair })`, used by both graphs, so nothing is
  duplicated.
- **What the flag does.** `implement-ticket` passes `false` and is unchanged. `implement-slice` passes
  `true`: every code-changing repair routes through `map:reextract → map:drift` before `publish`

- **What repairs see.** Repair nodes read `slice.ghosts`, so fixes respect the approved design.

`core/validate.ts` has no optional-read form, so `map:extract` seeds `slice.drift` and
review_findings on the entry path. The scopes must match every other writer of those keys, including
the shared delivery nodes, or `declarations()` throws (`core/graph.ts:127`).

**Read-only proposer (D6/5A).** `slice.propose` runs with `permissionMode: "plan"`.
- **Enforced, not a default.** `Engine.resolveAgentConfig` treats a node's `readOnly: true` as a hard
  constraint that no run override, UI tuning or graph default can raise. Today a run override
  outranks the node setting.
- **Why it matters.** A proposer that writes files would change the worktree fingerprint and
  invalidate its own proposal.
- **Tests:**
  - the resolved config for `slice.propose` is read-only even with `--permission-mode bypassPermissions`;
  - a fingerprint change during proposal reports `stale: worktree changed during slice.propose`.

**`map.neighbourhood`** is how the proposer sees the map without query tools (those arrive in sprint
(b)).
- **What's in it:** a bounded list of existing block and entity identity keys, with their
  responsibilities, tiers and file paths.
- **Where it goes:** rendered into `prompts/slice.propose.md`, so it is inside `rendered_hash`.
- **How it's scoped:** entities the ticket names, expanded 2 hops.
- **How ticket-named entities are found:** deterministically. File paths, route strings and symbol
  names in `goal`/`work` are matched against snapshot keys (exact, then suffix). With no match, the
  operator picks an entry point, recorded as an event.

#### Decisions and the gate (1a)

**Proposal identity (D15).**
- The engine appends `ghost-proposed {proposal_id, proposal_hash, ghosts}` right after the `GhostSet`
  validator accepts `slice.propose`'s write.
- `proposal_id` is unique per round (the event's `seq` under the 0.5 lock). `proposal_hash` is
  `proposalHash(ghosts)` in `core/`: canonical JSON, then the same hash as `renderedHash`.
- An identical redraw gets a new `proposal_id`, so it is decidable.

**`engine/slice-decision.ts` (D7/6A)** is the only place that answers "what is the current proposal,
and what was decided?". The executor, the gate, replay and the routes all call it:
- `currentProposal(events)`: the latest `ghost-proposed`.
- `findDecision(events, proposal_id)`: the **first** `slice-approved` / `slice-feedback-sent` for that
  round.
- `isApproved(events, ghosts, manifestHash)`.

**Decision events** carry `{proposal_id, proposal_hash, manifest_hash}`. Feedback also carries
`comment_ids`.
- **Routes:** `approve`, `send-feedback` and `redesign` (CLI and web). They go through one shared
  module, alongside `resolveReply()`. Each decision is written with `EventLog.appendIf`:
  - Check that `proposal_id` is the current round.
  - If the round has **no decision**, append it.
  - If it has the **same decision**, it's an idempotent success.
  - If it has a **different decision**, refuse with "already approved at 14:02" (D5/4A, refined by D15).
- **Waking the run (D17).** The route then resolves the attention and calls `spawnResume`.
  `spawnResume` no longer trusts a live PID blindly: if the runner exits within a short grace period
  without consuming the decision, it resumes.
- **The decision alone is enough (D17).** `replayState` treats an `awaiting-approval` park as resolved
  once `findDecision` returns a decision for the current round. So `howdah up` (`cli/main.ts:222`)
  resumes the run on its next tick, even if the route crashed between append and resolve.

**Approval executor algorithm** (each attempt, including every resume):
1. Stale probe: compare the live worktree fingerprint to `map.base.fingerprint`. If stale, write
   `outcome: "stale"` and succeed.
2. `findDecision(events, currentProposal.proposal_id)`.
3. If found, write `outcome: "approved"` or `"feedback"` (with that event's comments) and succeed.
4. Otherwise return **`awaiting`**. The engine then (D4/3A):
   - calls `ctx.endAttempt("failed")`, restoring veiled `cleared` keys;
   - appends **no** `node-finished`, so replay keeps the node mid-flight;
   - parks with code `awaiting-approval`.

   Resume re-attempts the same visit (`run.ts:184`), so waiting never consumes a visit. Logging
   `node-finished` here would let a restart route onward on the previous visit's write.

**The `requires` gate (D3/2A)** is a pre-start check in `Engine.loop`, beside `maxVisits`
(`run.ts:215-217`), **before** `node-started`. It consumes no visit.
- **Why it exists:** `jump` can move a stopped run straight to `implementation.implement`, past
  `slice.approve`.
- **What it checks:**
  - `isApproved(...)` for the current round;
  - on the **first** implement attempt after each approval, the **live** worktree fingerprint equals
    `map.base.fingerprint` (D18). Reject-loop re-entries are exempt, because implement's own changes
    are authorised.
- **How it fails:**
  - no current approval: park with code `approval-missing`;
  - live fingerprint mismatch: park with code `stale-base`, including a diff summary.
- **Event sources:** both gates read only decision events, never `attention-resolved`, because
  `resume()` auto-resolves parks (`run.ts:180`).

**Fingerprint (D18)** = HEAD, plus a hash of `git status --porcelain`, the working diff, and the
*contents* of untracked, non-ignored files. `probeGit` (`engine/reconcile.ts`) gains a
`fingerprint()` alongside `uncommitted`. Stale means the fingerprint **changed**, not that the tree is
dirty. `map:extract`'s `maxVisits: 5` parks a base that keeps moving.

**Redesign (D22).** `redesign <run> <msg>`:
- appends `slice-redesign-requested {message}`, then jumps to `map:extract` with budgets reset;
- `map:extract` seeds `slice.feedback` from unconsumed redesign requests;
- the message reaches the `slice.propose` prompt exactly once.

Plain `jump` stays for non-slice graphs.

**Approval node kind: what it touches.**
- `engine/run.ts`: `AttemptResult.status` gains `"awaiting"`, plus the `requires` pre-start check and
  budget floors.
- `EngineOpts.executors` gains `approval`.
- `core/graph.ts`: `ApprovalNode`, `requires` and `readOnly`. `core/validate.ts` adds its writes to
  the MUST-analysis.
- `engine/executors/index.ts`, `engine/replay.ts` (decision-resolved parks, budget floors),
  `log/events.ts`, `web/derive.ts`, `web/server.ts`, `cli/main.ts`, `web/app/main.tsx`.
- Value validation uses small hand-written TS validators, declared per write next to the scope
  (`core/graph.ts:48`). Agent writes are validated in `executors/outputs.ts`, which today checks keys
  only (`outputs.ts:70`).

#### Extraction (1b)

**Input files (D9/8A).** `git ls-files` at the base commit, plus the worktree diff.
- Files over 1 MB, and paths matching a small generated-code list (`generated/`, `*.min.js`, OpenAPI
  client dirs, lockfiles), are skipped.
- Each skip is recorded as `skipped: {path, reason}` in the manifest, never silently.

**Parsing.**
- web-tree-sitter (WASM); the native bindings fail under bun (verified). Grammars: Kotlin, Java,
  TypeScript/TSX.
- A **Bun Worker pool**, one worker per core, handles cold parses (D13/12A). `map-progress
  {done, total, skipped}` events stream to the log so the viewer shows movement.
- Every parser `ERROR` region becomes an "unparsed region" fact. The Kotlin grammar v1.1.0 fails on
  Kotlin 2.2 syntax (verified). A grammar that fails to load becomes a `not-checked` fact for every
  file in that language, never a crash.

**Adapters** are small, separate `.scm` query files joined in code, because combined queries silently
dropped matches in local tests.
- **http4k routes**, including nested `bind routes(...)` prefixes.
- **React fetch / react-query call sites.**
- **Coverage (D20).** Each adapter declares the constructs it covers. A file with unrecognised
  candidate constructs (for example a `routes(` call it couldn't resolve) is marked
  **partial coverage** for that adapter.
- **Frontend → backend join:** emits `exact`, `pattern-match (N candidates)` or `unresolved(reason)`,
  never a single guessed edge. An OpenAPI join is an optional adapter.

**Storage (D14/13A + D23).**
- **One immutable, content-addressed object store** at `$HOWDAH_HOME/maps/objects/<hash>.json` holds
  per-file **path-independent syntax facts**: declarations, calls, casts, routes, local names.
  - The key is `content hash + grammar version + query-file hash + adapter version`.
  - It doubles as the parse cache.
- **A run snapshot** is a small manifest at `runs/<run-id>/maps/<manifest-hash>.json`. It contains
  `{file → object hash}`, plus hashes of the build and package manifests (`settings.gradle.kts`,
  `build.gradle.kts`, `package.json`, `tsconfig.json`), plus skips.
- **Snapshot assembly** adds path, module membership and identity keys. So identical bytes at two
  paths are two entities, and moving a file between Gradle modules changes its block.
- Objects are never pruned while a manifest references them. Garbage collection is TODO P3.

**Identity keys (D8/7A).**

| Entity | Identity key |
|---|---|
| Block | repo-relative module path (Gradle project path + package for JVM; package dir for TS) |
| Route | `METHOD + normalised path template` (`{id}`, `:id`, `${id}` → `{*}`), prefixes joined |
| Function (JVM) | `pkg.Class.method(ParamType,…)`, using the declared type text; extension: `pkg.<ext Recv>.name(…)`; top-level: `pkg.<top>.name(…)` |
| Function (TS) | `module-path#exportName[.member]` |
| Fetch site | enclosing function id + `METHOD + normalised template` |
| Edge | `(from id, to id, kind)` where kind ∈ import, call, route-handler, fe→be |

- **Collisions.** If the assembled snapshot still has duplicate keys, every duplicate is marked
  **ambiguous** and can never verify. Drift reports it as `not-checked (ambiguous)`.
- **Tier and evidence.** Each observed entity and edge carries `tier` and `evidence: file:line`.
- **Tier order:** observed > resolved > syntactic > evidence-checked > unresolved.

#### Ghosts and drift (1c)

```ts
type Op = "add" | "modify" | "remove" | "keep";
interface GhostSet {
  blocks: { id: string; op: Op; plane?: string; responsibility: string }[];
  entities: { id: string; op: Op; block: string; kind: "route" | "function" | "fetch-site";
              expected_file: string; names?: string[] }[];
  edges: { from: string; to: string; kind: "import" | "call" | "route-handler" | "fe-be"; op: Op }[];
  trace: { scenario: string; steps: string[] /* entity ids, in order */ }[];
}
```

- **Ids are identity keys.** `comment-pinned.entity_id` is one of them, or `from→to:kind` for an edge.
- **Comments across redraws.** A comment survives a redraw when its key is still present. When the
  key disappears, the comment is shown as **orphaned**, never dropped.
- **Where the proposer learns the schema:** `prompts/slice.propose.md`, which is pinned and inside
  `rendered_hash`.
- **Validator (next to the node declaration):**
  - ids with op `modify` / `remove` / `keep` must exist in the base snapshot;
  - ids with op `add` must parse under the key grammar and must not already exist;
  - every entity declares an `expected_file` (D20).
- **Unverifiable text.** `responsibility` and `names` are prose. They are shown but never verified,
  and are labelled that way.

**Drift (D19/19A)** is computed deterministically by `map:drift` from **base vs after**. An LLM may
only explain it.

| Ghost op | `verified` when | Otherwise |
|---|---|---|
| `add` | absent in base, present in after | `missing` (only if searchable, below) |
| `modify` | present in both, entity content hash changed | `unchanged` |
| `remove` | present in base, absent in after | `still-present` |
| `keep` | present in both, content hash unchanged | `changed-unexpectedly` |

- **`unexpected`**: an entity that changed between base and after with no ghost for it.
- **`missing` needs proof (D20).** It is reported only when the ghost's `expected_file` (or module) was
  searched with **full coverage** by an adapter that covers the ghost's kind. Otherwise the result is
  `not-checked (reason)`: partial coverage, unparsed region, ambiguous key, a tier that didn't run, or
  a skipped file.
- **Traces:** `verified` when every consecutive step pair is a verified edge, `partial` when some are,
  and `not-checked` when any needed tier didn't run.
- **Size limit:** `slice.drift` is a per-ghost list `{key, op, outcome, evidence}`, capped at 200 with
  a truncation count.
- **Commit stamp:** each `drift-detected` event records the commit it checked, and the UI shows which
  commit "verified" refers to (D21).

**Map built-ins.** `map:extract`, `map:reextract` and `map:drift` are built-ins alongside `probe:pr`,
not shell commands.
- **Why not a shell command:** `commandExecutor` (`engine/executors/worktree.ts:145-190`) ignores the
  `reads` that `ExecArgs` already carries (`run.ts:47`), streams all stdout as `chunk` events, and
  can't emit typed events.
- **What the built-ins do instead:** they run in-process with the node's reads, write manifests and
  objects, append `map-extracted` / `map-progress` / `drift-detected`, and return bounded writes only.

**Events** (additive, in `log/events.ts`):
- `map-extracted {manifest_hash, commit, fingerprint, tiers_run, unparsed, skipped}`
- `map-progress`
- `ghost-proposed {proposal_id, proposal_hash, ghosts}`
- `comment-pinned {id, entity_id, proposal_id, text}`
- `slice-feedback-sent {proposal_id, proposal_hash, manifest_hash, comment_ids}`
- `slice-approved {proposal_id, proposal_hash, manifest_hash}`
- `slice-redesign-requested {message}`
- `drift-detected {commit, outcomes}`
