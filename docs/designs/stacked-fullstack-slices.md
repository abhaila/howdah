# Stacked full-stack slices: one plan, a BE and an FE stack, merged one by one

Generated by /plan-eng-review on 2026-10-13, against `origin/main` a8e3a98.

## The ask

Give Howdah one plan for a big project that spans a backend repo and a frontend repo. For each
slice, run a BE implement-ticket and an FE implement-ticket. Each side is a stack of PRs. Teammates
review every PR, and the PRs merge one at a time.

## What already exists

| Need | Existing piece |
|---|---|
| Decompose, approve, ticket and launch | `plan-feature` + `runs:launch` (HOW-23) |
| A slice in a chosen repo | `Slice.workspace` (`graphs/slice-plan.ts:38`) |
| Ordering between slices | `Slice.depends_on`, but ADVISORY: every child launches at once (`launch.ts:12-16`) |
| Publish and watch a stack of PRs in one run | `delivery.publish` stack rules (525653e), `probe:pr` stack state (661c857) |
| Wait, probe, repair loop | `delivery.wait` (5m) → `delivery.probe_pr` → repair agents |
| Reading another run's state | `replayState(readLog(...))`, `worktree.json` |
| Effects done exactly once | `effects.claim()` / `done()` |

## What is missing (the four features)

1. **A run cannot wait for another run.** `depends_on` is prose.
2. **A worktree cannot start from a given branch.** `worktree.ts:70` runs `git worktree add -b <branch> <path>` with no start point, so EVERY run today branches from the operator's clone's current HEAD.
3. **A run cannot read another run's results** (branch, tip, PR, state).
4. **Nothing restacks** an upper PR when the PR below it changes or squash-merges.

GitHub retargets an open PR to `main` when its base branch is deleted after a merge. But after a squash merge the upper branch still carries the lower PR's commits, so it has to be replayed with `git rebase --onto origin/main <old lower tip>` ([GitHub docs: merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request)).

## Design

```
 plan-feature: decompose → approve → tickets → runs:launch (ALL children at once, as today)
   slices:  be-1                    fe-1 {be-1: package}
            be-2 {be-1: published}  fe-2 {fe-1: published, be-2: package}
        │   a slice with depends_on launches implement-stacked, otherwise implement-ticket
        ▼
 ┌──────────────────────────── implement-stacked = stackedFrom(implement-ticket) ────────────┐
 │ deps.await (runs:await) ◀── wait (5m → 15m → 30m back-off; waits never count as steps)   │
 │    each dependency (by `<parent>--<slice>`):                                            │
 │      dir missing but parent logged run-spawned → not ready yet                           │
 │      dir missing and no spawn record           → PARK "never launched"                   │
 │      running / parked                           → keep waiting, say on what              │
 │      failed / aborted / closed unmerged         → PARK with its state                    │
 │      published | merged | package (until)      → ready                                   │
 │    publishes deps.ready, deps.base (head branch of the published dep's PRIMARY PR,       │
 │    else its worktree branch), deps.base_tip (PR head oid), deps.prs                      │
 │        ▼ ready                                                                           │
 │ create_worktree   fetch; branch from deps.base (else origin/<default>)             (7A)  │
 │        ▼  every agent step carries the STACKED suffix: "stacked on <branch>@<sha>;       │
 │           your change is <sha>..HEAD; do not modify or review the base's commits"        │
 │ … every implement-ticket node (plan, implement, verify, evidence, review) …            │
 │        ▼                                                                                 │
 │ delivery.publish  = stacked.publish ({{> delivery.publish}} + target deps.base,          │
 │                     object-form summary required)                                       │
 │        ▼                                                                                 │
 │ wait ─▶ deps.probe (runs:await, probe mode) ─▶ probe_pr                                  │
 │           │ routes, highest weight first (pinned by test):                               │
 │           ├─ base MERGED                         ─▶ git:restack onto origin/<default>     │
 │           ├─ base MOVED and this PR not approved ─▶ git:restack onto the new base tip     │
 │           ├─ CONFLICTS / CI / reviews            ─▶ today's repairs                       │
 │           └─ otherwise                           ─▶ wait                                 │
 │   git:restack: rebase --onto <target> <recorded tip>; push --force-with-lease (this run's│
 │   branch only); retarget the PR if GitHub didn't; append `base-restacked {from,to}`;     │
 │   effects.claim/done. A conflict aborts the rebase and goes to the repair agent WITH the │
 │   exact --onto command (never the plain "rebase onto target").                          │
 │        ▼ MERGED (probe:pr ignores every URL in deps.prs)                                 │
 │ cleanup, done                                                                            │
 └──────────────────────────────────────────────────────────────────────────────────────────┘
```

### Decisions

| # | Decision | Why |
|---|---|---|
| **D1-A** | Full stacks across runs: all four features. | Stacking is the point. Merge-gated waves would serialise a 6-slice project on review latency. |
| **1A** | The CHILD waits, through a new `runs:await` built-in in a wait loop. All children launch at once, and the parent never supervises. | Keeps the HOW-23 invariant and reuses the delivery wait→probe pattern. |
| **2A + G10** | `depends_on: [{ slice, until: "published" \| "merged" \| "package" }]`. The old string form means `merged`. `package` means merged AND the workspace's `packageCheck` command (config.json, like `verifyCommand`) exits 0; with no command configured it behaves as merged and says so. **At most one `published` dependency per slice, and it must be in the same workspace**: that one is the stack base. | Stacking needs `published`. An FE consuming the BE's OpenAPI package needs the package, not just the merge. |
| **3B** | A separate `implement-stacked` graph. `implement-ticket` keeps its shape (it gains only 7A, at executor level). | Your call. |
| **5A + G3** | `implement-stacked = stackedFrom(implementTicketSpec)`. It inserts `deps.await` and its wait before `create_worktree`, and `deps.probe` before `probe_pr` in the delivery loop. It gives `create_worktree` its base read, points publish at `stacked.publish`, and adds the restack routes. The drift test asserts every implement-ticket NODE is present, and every edge is present or in a named, tested list of rewired edges. | Two graphs with no silent drift, and the guarantee stated honestly. |
| **A (supersedes 4B)** | A deterministic `git:restack` built-in, wrapped in effects and appending `base-restacked`. Only a conflict reaches the repair agent. Decision 9c6359d8 (supersedes 6579a2f3). | An agent step cannot append events or move the recorded tip, so the bookkeeping must live in an executor. |
| **B (revises 6A)** | Restack when the base MERGES, and when the base MOVES while this PR has no approving review. Never re-push an approved PR because its base moved. | Avoids CI churn and dismissed approvals. Reviewers still see a clean diff. |
| **C (refines 7A)** | Every worktree branches from `origin/<default>` (or `deps.base`) after a fetch. Record local HEAD beside the chosen base. When HEAD has commits origin lacks, log "your local main is N commits ahead; not used". With no remote or a failed fetch, use HEAD and log it. | Fixes a silent bug for every run, visibly. |
| **G1** | A missing dependency dir is "not ready" while the parent's log has `run-spawned` for it. | Children are detached and may not have written their first line yet (`launch.ts:150`). |
| **G2** | A stacked publish must use the object summary form, and `probe:pr` drops any URL in `deps.prs`. | Otherwise fe-2 watches fe-1's PR and completes when fe-1 merges (`worktree.ts:134-137` takes the first link). |
| **G4** | Base-merged and base-moved routes outweigh CONFLICTS. | `resolve_conflicts` says "rebase onto the target", which is wrong after a squash merge. |
| **G5** | Wait steps don't count toward `maxSteps`, and the await wait backs off 5m → 15m → 30m while nothing changes. | 1000 steps (`run.ts:442`) at 5m is about 41h, and stacks wait for days. |
| **G6** | A parked dependency is still waited on. Only a non-success terminal state parks the dependent. | A park is normal control flow, and cascades would be noise. |
| **G7** | The base is the head branch of the dependency's primary PR (`gh pr view --json headRefName,headRefOid`), falling back to its worktree branch. | A dependency may have published its own in-run stack. |
| **G8** | A versioned STACKED suffix on every agent step of implement-stacked, rendered from `deps.base`/`deps.base_tip`, so it reconstructs VERIFIED. | Planning and review must judge only `<tip>..HEAD`. |
| **G3b** | `stacked.publish.md` = `{{> delivery.publish }}` plus the stacked rules. `delivery.publish` is unchanged. | A shared `{{#if deps.base}}` would make implement-ticket read a field it never writes. |
| **G9** | Add implement-stacked to `graphs/fixtures/pre-spec-shapes.json` by hand, with a dated note. Every existing entry stays byte-identical. Built-ins are already `builder:false`. | A new graph is not a conversion. |
| **G11** | The child graph is chosen per slice everywhere `CHILD_GRAPH` is used (`launch.ts:61,158,245,301`). `deps` travels as a JSON string declared in implement-stacked's inputs. Includes an argv round-trip test through `core/launch-args.ts`. | It is the one argv builder both launch paths share. |
| **8A** | A real-git E2E against a local bare "origin". (The restack prompt eval is dropped: restack is code now.) | The risky operation is proven before it touches a real stack. |

## Failure modes

| Path | Realistic failure | Test | Operator sees |
|---|---|---|---|
| await | a dependency hasn't written its first line yet | S3 | nothing; it keeps waiting (G1) |
| await | a dependency was closed without merge | S3 | a park naming it and its PR |
| await | waiting for days | S4 | no max-steps park (G5) |
| worktree | fetch fails offline | S2 | the run starts from HEAD, and a logged fact says so |
| worktree | local main has unpushed commits | S2 | "your local main is N commits ahead; not used" |
| restack | rebase conflict | S5, S8 | the repair agent gets the exact --onto command; it may park with the files |
| restack | a push races a teammate's push | S5 | `--force-with-lease` refuses; the restack retries next probe |
| probe | the summary cites the base PR first | S6 | still watches its own PR (G2) |
| launch | an old plan uses string `depends_on` | S1 | treated as merged |
